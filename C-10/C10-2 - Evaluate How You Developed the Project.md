##**Original Requirements Compared With the Finished Software**

The original requirements generally matched the finished EduTrack software. The main purpose of the project was to help teachers manage student work that was Missing, Late or Submitted. The finished software provides student management, status management, filtering, searching, reminders and data storage, which directly support this purpose.

The Must Have requirements were mostly achieved. The software allows teachers to manage student records and update statuses. The finished software also includes several features that were originally identified as Should Have or Could Have requirements, such as filtering and reminders.

Some requirements were only partly achieved. The filtering system works, but beta testers found it less natural to use than expected. The original requirement also expected automatic saving of status changes, which could be improved in the final software. Some features from the original SRS, such as Canvas integration, mobile access and cloud synchronisation, were outside the project scope and were therefore not expected in the final product.



**Original Designs Compared With the Finished Software**

The original designs provided a useful starting point for the final interface. Important functions such as updating statuses, filtering students and managing records were included in the designs and were later developed into the finished software.

The design evaluation showed that both designs supported important functions such as updating statuses, marking work as Late or Submitted, filtering, usability, reliability and portability. However, some features such as searching, saving/loading data and security were not fully represented in the original designs.

The final product therefore developed beyond the original sketches by including a complete login system, student management pages, reminders, reports, search and additional filtering controls.



**Important Differences Between the Original Designs and Final Product**

One important difference was that the original designs were focused more generally on managing assignments, while the final product became more focused on managing student records.

The final software also included features that were not fully shown in the original designs, including:

Login and account creation
A sidebar navigation system
Student profiles
Missing Work Reminders
Reports
Student ID searching
Separate filtering controls
JSON-based account and student data storage

The final interface was therefore more developed and functional than the original sketches.



**Analysis - What Could Have Been Done Better**

During analysis, I could have gathered more detailed information about the teacher's preferred workflow before starting the design.

This would have helped identify usability issues earlier, particularly the login process, input requirements and filtering system. More detailed user research could have reduced the amount of changes needed later.



**Design - What Could Have Been Done Better**

During design, I could have made the buttons and filtering controls more prominent and easier to understand.

Beta testing showed that some testers had difficulty locating the Add, Edit and Remove Student buttons and found the filtering system less natural to use. Designing these controls more clearly from the beginning would have reduced these issues.



**Development - What Could Have Been Done Better**

During development, I could have tested individual features with users earlier instead of waiting until the main beta-testing stage.

Earlier testing would have allowed problems with login, input instructions, button visibility and filtering to be identified and fixed before the final testing stage. This would also have reduced the amount of refinement required near the end of the project.

**Analysis → Design → Development**

The Analysis stage identified the problem with managing Missing, Late and Submitted student work and established the requirements for the software.

The Design stage then used these requirements to plan the interface, features, filtering system and student management functions.

The Development stage turned these designs into the working EduTrack application using Python and Tkinter. Testing during development and beta testing then identified areas that could be improved.
